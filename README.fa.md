# کاغذ آنلاین

[English](README.md)

کاغذ آنلاین یک وب‌اپلیکیشن برای نوشتن و اشتراک‌گذاری سند است. این پروژه از ابتدا
برای زبان فارسی طراحی شده و رابط کاربری آن راست‌چین است. ویرایشگر از فونت وزیرمتن
استفاده می‌کند.

کاربر سند را در ویرایشگر می‌نویسد، سطح دسترسی آن را تعیین می‌کند و لینک را در
اختیار دیگران قرار می‌دهد. سند می‌تواند عمومی، خصوصی یا عمومی با رمز عبور باشد.
همچنین هر کاربر می‌تواند تعدادی از اسناد خود را در پروفایل شخصی‌اش منتشر کند.

## دمو

- نسخه آنلاین: https://kaghaz-online.vercel.app
- سورس‌کد: https://github.com/Arshnme/kaghaz-online

## امکانات

**حساب کاربری**
ثبت‌نام با ایمیل و رمز عبور انجام می‌شود و تأیید ایمیل اختیاری است. ورود از طریق
OAuth نیز پشتیبانی می‌شود. کاربر در هنگام ثبت‌نام نام کاربری انتخاب می‌کند. این نام
هم در سمت مرورگر و هم در سمت سرور بررسی می‌شود و نباید در فهرست نام‌های رزروشده
(`reserved-usernames.json`) قرار داشته باشد. هدف از این محدودیت، جلوگیری از
سوءاستفاده از نام‌هایی مانند `admin` یا `dashboard` است.

**نوشتن:**
ویرایشگر بر پایه TipTap ساخته شده و امکاناتی مانند تیتر، فهرست، نقل‌قول، بلوک کد،
لینک، تصویر، فایل پیوست، متن ضخیم، کج، زیرخط، خط‌خورده، رنگ متن، هایلایت، انتخاب
فونت، اندازه فونت و ترازبندی را فراهم می‌کند. سند پس از تایپ با کمی تأخیر به‌صورت
خودکار ذخیره می‌شود.

**اشتراک‌گذاری:**
هر سند می‌تواند عمومی یا خصوصی باشد. امکان قرار دادن رمز عبور روی اسناد عمومی نیز
وجود دارد. گزینه سوم، انتشار در پروفایل است؛ در این حالت سند در صفحه پروفایل
نویسنده نمایش داده می‌شود اما در فهرست‌های عمومی ظاهر نمی‌گردد.

**فایل پیوست:**
هر سند می‌تواند فایل پیوست داشته باشد. فایل‌ها در باکت خصوصی Supabase Storage
نگهداری می‌شوند و تنها از طریق API قابل دسترسی هستند. این API پیش از ارائه فایل،
دسترسی کاربر به سند را بررسی می‌کند. نام فایل نیز رمزنگاری می‌شود.

**داشبورد:**
داشبورد دو نمای شبکه‌ای و فهرستی دارد و امکان جستجو، فیلتر بر اساس وضعیت عمومی یا
خصوصی بودن اسناد و جابه‌جایی اسناد با کشیدن و رها کردن را فراهم می‌کند. ترتیب جدید
ذخیره می‌شود.

**پروفایل:**
هر کاربر دارای یک صفحه عمومی در مسیر `/[username]` است. در این صفحه اسناد منتشرشده
به‌همراه تعداد بازدید و پسند هر کدام نمایش داده می‌شود. صاحب پروفایل می‌تواند نام
نمایشی، بیوگرافی، وب‌سایت، موقعیت جغرافیایی، تصویر پروفایل (همراه با امکان برش
تصویر)، نام کاربری و رمز عبور را ویرایش کند.

## رمزنگاری:

رمزنگاری به‌طور کامل در سمت سرور و در فایل `lib/crypto.ts` انجام می‌شود. این فایل از
ماژول `crypto` داخلی Node.js استفاده می‌کند که در مرورگر در دسترس نیست. بنابراین
عملیات رمزنگاری و رمزگشایی هرگز در سمت کاربر اجرا نمی‌شود و هیچ کلیدی به مرورگر
ارسال نمی‌گردد.

| مورد | مقدار |
|------|--------|
| الگوریتم | AES-256-CBC |
| کلید | SHA-256 از مقدار `ENCRYPTION_KEY` |
| مقدار اولیه (IV) | ۱۶ بایت تصادفی برای هر مقدار |
| قالب ذخیره | `<iv>:<ciphertext>` (هر دو به صورت hex) |

مقدار اولیه برای هر داده جدید به‌صورت جداگانه تولید می‌شود. در نتیجه دو سند با
محتوای یکسان، داده رمزشده یکسان نخواهند داشت.

موارد زیر رمزنگاری می‌شوند:

- عنوان سند (`documents.title`)
- محتوای سند (`documents.content`)
- رمز عبور سند (`documents.password`)
- نام اصلی فایل پیوست (`document_files.original_filename`)

رمزنگاری در فرآیندهای ساخت سند، ویرایش سند، بارگذاری فایل و خواندن سند اعمال
می‌شود. محتوای اسناد هرگز به‌صورت خام در پایگاه‌داده ذخیره نمی‌گردد.

موارد زیر رمزنگاری نمی‌شوند:

- اطلاعات پروفایل (نام کاربری، ایمیل، نام نمایشی، بیوگرافی، وب‌سایت و موقعیت)
- متادیتای سند (وضعیت عمومی یا خصوصی، ترتیب نمایش، تعداد بازدید و پسند، تاریخ‌ها)
- شناسه عمومی سند (`document_id`) که در آدرس صفحه استفاده می‌شود
- خود فایل‌های پیوست (این فایل‌ها به‌صورت خام در باکت خصوصی نگهداری می‌شوند و تنها
  نام آن‌ها رمزنگاری می‌گردد)

محتوای سند رمزنگاری می‌شود اما متادیتا رمزنگاری نمی‌شود. در صورت نیاز به رمزنگاری
متادیتا، این قابلیت باید به‌صورت جداگانه پیاده‌سازی شود.

## پشته فناوری

| لایه | انتخاب |
|------|--------|
| فریم‌ورک | Next.js 15 با App Router |
| رابط کاربری | React 19، Tailwind CSS و shadcn/ui بر پایه Radix |
| ویرایشگر | TipTap نسخه ۲ |
| بک‌اند | Supabase (PostgreSQL، احراز هویت و Storage) |
| زبان | TypeScript با حالت strict |
| میزبانی | هر محیطی که از Next.js پشتیبانی کند؛ Vercel ساده‌ترین گزینه است |

سرویس بک‌اند جداگانه‌ای وجود ندارد. Server Component‌ها صفحات را رندر می‌کنند،
Client Component‌ها تعاملات کاربری را مدیریت می‌کنند و عملیات نیازمند دسترسی سطح
بالا در route handler‌های مسیر `app/api/` انجام می‌شود.

## نصب و راه‌اندازی

برای اجرای پروژه به Node.js نسخه ۲۰ یا بالاتر و یک پروژه Supabase نیاز است. پلن
رایگان برای شروع کافی است.

```bash
git clone https://github.com/Arshnme/kaghaz-online.git
cd kaghaz-online
npm install
```

فایل `database/01-schema.sql` را در SQL Editor پنل Supabase اجرا کنید. این فایل
جداول، ایندکس‌ها، سیاست‌های Row Level Security، توابع، تریگرها و باکت‌های
ذخیره‌سازی را ایجاد می‌کند. در صورت تمایل می‌توانید پس از آن فایل
`database/02-sample-data.sql` را نیز اجرا کنید تا داده‌های نمونه برای آزمایش در
اختیار داشته باشید.

سپس متغیرهای محیطی را تنظیم نمایید:

```bash
cp .env.example .env.local
openssl rand -base64 32   # ENCRYPTION_KEY
openssl rand -base64 32   # JWT_SECRET
```

آدرس و کلیدهای مربوط به Supabase را وارد کرده و دستور زیر را اجرا کنید:

```bash
npm run dev
```

برنامه در آدرس `http://localhost:3000` در دسترس خواهد بود.

راهنمای کامل‌تر، از جمله نکات مربوط به تنظیمات احراز هویت Supabase، در فایل
`docs/deployment.md` موجود است.

## متغیرهای محیطی

| متغیر | ضروری | توضیح |
|-------|--------|--------|
| `NEXT_PUBLIC_SUPABASE_URL` | بله | به صورت `https://<project-ref>.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | بله | کلید عمومی که به مرورگر ارسال می‌شود؛ حفاظت از داده‌ها بر عهده Row Level Security است |
| `SUPABASE_SERVICE_ROLE_KEY` | بله | تنها در سمت سرور استفاده می‌شود و Row Level Security را دور می‌زند. نباید هرگز به مرورگر ارسال شود |
| `ENCRYPTION_KEY` | بله | کلید رمزنگاری اسناد. در صورت گم شدن یا تغییر، اسناد قبلی قابل خواندن نخواهند بود |
| `JWT_SECRET` | بله | برای امضای توکن نشست |
| `GOOGLE_SITE_VERIFICATION` | خیر | در صورت تنظیم، به‌صورت متا تگ در صفحه قرار می‌گیرد |
| `YANDEX_SITE_VERIFICATION` | خیر | مشابه مورد بالا |

## دستورها

```bash
npm run dev        # اجرای سرور توسعه
npm run build      # ساخت نسخه production
npm run start      # اجرای نسخه production
npm run lint       # بررسی با ESLint
npm run typecheck  # بررسی نوع‌ها با tsc --noEmit
```

## ساختار پروژه

```
app/                    صفحات App Router و route handler‌های API
  api/                  دسترسی به داده با سطح دسترسی بالا
  dashboard/            فهرست اسناد
  editor/[id]/          ویرایشگر
  [username]/           پروفایل عمومی
components/
  ui/                   اجزای پایه shadcn/ui
  auth/ dashboard/ editor/ public/
```

جزئیات بیشتر درباره مدل داده و لایه‌های کنترل دسترسی در فایل
`docs/architecture.md` توضیح داده شده است.

## نکات امنیتی

پیش از انتشار عمومی پروژه، توجه به موارد زیر ضروری است:

- کلید `service role` به‌طور کامل Row Level Security را دور می‌زند و در route
  handler‌های مسیرهای `app/api/auth/`، `app/api/profile/`، `app/api/documents/` و
  `app/api/files/` استفاده می‌شود. به همین دلیل این handler‌ها خود مسئولیت بررسی
  مالکیت رکوردها را بر عهده دارند و نباید به RLS تکیه کنند. این کلید باید صرفاً در
  سمت سرور نگهداری شود.

- مقدار `ENCRYPTION_KEY` بدون انجام مهاجرت قابل تغییر نیست. در صورت تغییر آن، عنوان
  و محتوای تمام اسناد قبلی و همچنین نام فایل‌های پیوست آن‌ها غیرقابل خواندن خواهد
  شد. تابع `decrypt` در چنین شرایطی به‌جای ایجاد خطا، متن رمزشده را بازمی‌گرداند.
  این رفتار عمدی است تا یک رکورد آسیب‌دیده باعث از کار افتادن کل صفحه نشود. توصیه
  می‌شود از این کلید نسخه پشتیبان تهیه و در مکانی امن نگهداری شود.

- رمز عبور اسناد رمزنگاری می‌شود و نه هش. هنگام باز کردن سند، رمز رمزگشایی شده و
  مقایسه می‌گردد. این روش به دلیل نیاز به متن اصلی برای مقایسه انتخاب شده است. در
  نتیجه هر فردی که به `ENCRYPTION_KEY` دسترسی داشته باشد می‌تواند رمز عبور اسناد
  اشتراکی را مشاهده کند. به کاربران توصیه کنید از رمزهای عبور مهم خود برای این
  منظور استفاده نکنند.

مقادیر `JWT_SECRET` و `ENCRYPTION_KEY` به‌صورت پیش‌فرض تنظیم نشده‌اند. در صورت عدم
تعریف آن‌ها، عملیات وابسته با خطا مواجه می‌شوند. دلیل این طراحی آن است که هر مقدار
پیش‌فرضی که در مخزن عمومی قرار گیرد، دیگر به‌عنوان راز محسوب نمی‌شود.

## وضعیت پروژه

پروژه در حال حاضر قابل استفاده است. با این حال چند بخش هنوز تکمیل نشده‌اند:

- فایل‌های آیکون مورد اشاره در `app/layout.tsx` و `public/manifest.json` در مخزن
  موجود نیستند. فهرست آن‌ها در `public/README.md` آمده است.
- مسیرهای `/terms`، `/privacy` و `/about` در فرم ثبت‌نام و sitemap ذکر شده‌اند اما
  صفحات مربوط به آن‌ها هنوز پیاده‌سازی نشده‌اند.
- مسیر `app/api/analytics/track/route.ts` تنها یک پیاده‌سازی اولیه است. مسیر
  `app/api/check-username/route.ts` نیز کار می‌کند اما در حال حاضر فراخوانی
  نمی‌شود؛ فرم ثبت‌نام بررسی آزاد بودن نام کاربری را مستقیماً از طریق Supabase انجام
  می‌دهد.
- جداول `document_comments` و `user_follows` در ساختار پایگاه‌داده تعریف شده‌اند اما
  رابط کاربری برای آن‌ها وجود ندارد.
- پکیج `@supabase/auth-helpers-nextjs` که در این پروژه استفاده می‌شود توسط Supabase
  کنار گذاشته شده و جایگزین آن `@supabase/ssr` معرفی شده است. مهاجرت به این پکیج از
  مهم‌ترین کارهای باقی‌مانده است. توضیحات بیشتر در `docs/architecture.md` آمده است.
- تست خودکار وجود ندارد. فرآیند CI تنها lint، typecheck و build را اجرا می‌کند.
