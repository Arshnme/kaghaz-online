# کاغذ آنلاین

[English](README.md)

کاغذ آنلاین یک وب‌اپلیکیشن برای نوشتن و اشتراک‌گذاری سند است. از ابتدا برای فارسی
ساخته شده؛ رابط کاربری راست‌به‌چپ است و ویرایشگر با فونت وزیرمتن می‌آید.

کاربر سند را در ویرایشگر می‌نویسد، تعیین می‌کند چه کسی آن را ببیند، و لینک را به
دیگران می‌دهد. سند می‌تواند عمومی باشد، خصوصی باشد، یا عمومی ولی پشت رمز. هر کس
هم می‌تواند چند سند از سندهایش را در پروفایل خودش منتشر کند.

## دمو

نسخه آنلاین: <https://kaghaz-online.vercel.app>

سورس کد: <https://github.com/Arshnme/kaghaz-online>

## امکانات

**حساب کاربری.** ثبت‌نام با ایمیل و رمز عبور، با تأیید ایمیل اختیاری. ورود با
OAuth هم پشتیبانی می‌شود. کاربر موقع ثبت‌نام نام کاربری انتخاب می‌کند. این نام هم
در مرورگر و هم در سرور بررسی می‌شود و نباید در فهرست نام‌های رزرو‌شده باشد
(`reserved-usernames.json`). دلیلش این است که کسی نتواند نام‌هایی مثل `admin` یا
`dashboard` را بردارد و خودش را جای مسئول سایت جا بزند.

**نوشتن.** ویرایشگر TipTap با تیتر، فهرست، نقل‌قول، بلوک کد، لینک، تصویر، فایل
پیوست، ضخیم، کج، زیرخط، خط‌خورده، رنگ متن، هایلایت، فونت، اندازه فونت و
ترازبندی چپ و وسط و راست. سند با کمی تأخیر بعد از تایپ خودش ذخیره می‌شود.

**اشتراک‌گذاری.** هر سند یا عمومی است یا خصوصی. روی سند عمومی می‌توان رمز گذاشت.
گزینه سومی هم هست: انتشار در پروفایل. یعنی سند در پروفایل نویسنده دیده می‌شود ولی
جای دیگری فهرست نمی‌شود.

**فایل پیوست.** هر سند می‌تواند فایل پیوست داشته باشد. فایل‌ها در یک باکت خصوصی
Supabase Storage می‌مانند و فقط با یک API خوانده می‌شوند که اول دسترسی به سند را
بررسی می‌کند. نام فایل هم رمزنگاری می‌شود.

**داشبورد.** دو نمای شبکه‌ای و فهرستی، جستجو، فیلتر بر اساس عمومی یا خصوصی بودن،
و جابه‌جایی سندها با کشیدن که ذخیره می‌شود.

**پروفایل.** هر کاربر یک صفحه عمومی در `/[username]` دارد، با سندهای منتشرشده و
شمار بازدید و پسند هر کدام. صاحب پروفایل هم می‌تواند نام نمایشی، بیوگرافی،
وب‌سایت، موقعیت، عکس پروفایل (با مرحله برش تصویر)، نام کاربری و رمز عبور را
عوض کند.

## رمزنگاری

رمزنگاری کاملاً سمت سرور انجام می‌شود، در فایل `lib/crypto.ts`. این فایل از ماژول
`crypto` خود Node استفاده می‌کند که در مرورگر وجود ندارد؛ پس رمزنگاری و رمزگشایی
هیچ‌وقت در سمت کاربر انجام نمی‌شود. هیچ کلیدی هم به مرورگر فرستاده نمی‌شود.

| مورد | مقدار |
| --- | --- |
| الگوریتم | AES-256-CBC |
| کلید | SHA-256 از مقدار `ENCRYPTION_KEY` |
| مقدار اولیه (IV) | ۱۶ بایت تصادفی، هر بار جداگانه برای همان مقدار |
| قالب ذخیره | `<iv>:<ciphertext>`، هر دو به شکل hex |

مقدار اولیه برای هر مقدار جدید از نو ساخته می‌شود. یعنی دو سند با متن یکسان،
داده رمزشده یکسان تولید نمی‌کنند.

این چهار مورد رمزنگاری می‌شوند:

- عنوان سند (`documents.title`)
- متن سند (`documents.content`)
- رمز عبور سند (`documents.password`)
- نام اصلی فایل پیوست (`document_files.original_filename`)

رمزنگاری در چهار مسیر انجام می‌شود: ساخت سند، ویرایش سند، آپلود فایل، و خواندن
سند. یعنی متن سند هیچ‌وقت خام روی دیتابیس نوشته نمی‌شود.

این موارد رمزنگاری نمی‌شوند و بهتر است بدانید:

- اطلاعات پروفایل: نام کاربری، ایمیل، نام نمایشی، بیوگرافی، وب‌سایت، موقعیت
- متادیتای سند: عمومی یا خصوصی بودن، ترتیب نمایش، شمار بازدید و پسند، تاریخ‌ها
- شناسه عمومی سند (`document_id`) که در URL می‌آید
- خود فایل‌های پیوست؛ این‌ها خام در باکت خصوصی Storage می‌مانند و فقط نامشان
  رمزنگاری می‌شود

پس متن سند رمزنگاری می‌شود، ولی متادیتا نه. اگر به رمزنگاری متادیتا هم نیاز
دارید، باید جداگانه اضافه شود.

## پشته فناوری

| لایه | انتخاب |
| --- | --- |
| فریم‌ورک | Next.js 15 با App Router |
| رابط کاربری | React 19، Tailwind CSS، و shadcn/ui روی Radix |
| ویرایشگر | TipTap نسخه ۲ |
| بک‌اند | Supabase — پستگرس، احراز هویت، فضای ذخیره‌سازی |
| زبان | TypeScript با حالت strict |
| میزبانی | هر جایی که Next.js اجرا شود؛ Vercel ساده‌ترین راه است |

سرویس بک‌اند جداگانه‌ای وجود ندارد. Server Component‌ها صفحه را رندر می‌کنند،
Client Component‌ها تعامل را مدیریت می‌کنند، و کارهای نیازمند دسترسی سطح بالا در
route handler‌های زیر `app/api/` انجام می‌شود.

## نصب و راه‌اندازی

به Node.js نسخه ۲۰ یا بالاتر و یک پروژه Supabase نیاز دارید. پلن رایگان کافی است.

```bash
git clone https://github.com/Arshnme/kaghaz-online.git
cd kaghaz-online
npm install
```

برای ساخت دیتابیس، فایل `database/01-schema.sql` را در SQL Editor پنل Supabase
اجرا کنید. این فایل جدول‌ها، ایندکس‌ها، سیاست‌های Row Level Security، توابع،
تریگرها و باکت‌های ذخیره‌سازی را می‌سازد. اگر خواستید بعد از آن
`database/02-sample-data.sql` را هم اجرا کنید تا چند کاربر و سند ساختگی برای تست
داشته باشید.

بعد متغیرهای محیطی را تنظیم کنید:

```bash
cp .env.example .env.local
openssl rand -base64 32   # ENCRYPTION_KEY
openssl rand -base64 32   # JWT_SECRET
```

آدرس و کلیدهای Supabase را وارد کنید و بعد:

```bash
npm run dev
```

برنامه روی `http://localhost:3000` بالا می‌آید.

راهنمای کامل، از جمله تنظیمات احراز هویت Supabase که اشتباه در آن‌ها رایج است، در
[docs/deployment.md](docs/deployment.md) آمده است.

## متغیرهای محیطی

| متغیر | ضروری | توضیح |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | بله | به شکل `https://<project-ref>.supabase.co`. برای بارگذاری تصاویر از پروژه Supabase هم استفاده می‌شود |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | بله | عمومی است و به مرورگر می‌رود؛ چیزی که از داده‌ها محافظت می‌کند Row Level Security است |
| `SUPABASE_SERVICE_ROLE_KEY` | بله | فقط سمت سرور. Row Level Security را دور می‌زند، پس نباید هرگز به مرورگر برود |
| `ENCRYPTION_KEY` | بله | کلید رمزنگاری سند. اگر گم شود یا عوض شود، سندهای قبلی خوانده نمی‌شوند |
| `JWT_SECRET` | بله | امضای توکن نشست |
| `GOOGLE_SITE_VERIFICATION` | خیر | اگر تنظیم شود، به‌صورت متا تگ رندر می‌شود |
| `YANDEX_SITE_VERIFICATION` | خیر | مانند بالا |

## نکات امنیتی

پیش از انتشار، دانستن این سه نکته لازم است.

**کلید service role به‌طور کامل Row Level Security را دور می‌زند.** این کلید در
route handler‌های `app/api/auth/`، `app/api/profile/`، `app/api/documents/` و
`app/api/files/` استفاده می‌شود. به همین دلیل این handler‌ها خودشان مالکیت رکورد
را بررسی می‌کنند و به RLS تکیه نمی‌کنند. کلید باید سمت سرور بماند.

**`ENCRYPTION_KEY` بدون مهاجرت قابل تغییر نیست.** با عوض کردنش، عنوان و متن همه
سندهای قبلی و نام فایل‌های پیوستشان خوانا نمی‌مانند. تابع `decrypt` در این حالت
به‌جای خطا دادن، متن رمزشده را همان‌طور برمی‌گرداند؛ این رفتار عمدی است تا یک
رکورد خراب کل صفحه را از کار نیندازد. از کلید نسخه پشتیبان نگه دارید، جایی که سال
بعد هم در دسترس باشد.

**رمز عبور سند رمزنگاری می‌شود، نه هش.** موقع باز کردن سند، رمز رمزگشایی و مقایسه
می‌شود. این کار عمدی است چون برای مقایسه به متن اصلی نیاز است. ولی یعنی هر کس
`ENCRYPTION_KEY` را داشته باشد می‌تواند رمز هر سند اشتراکی را بخواند. به کاربران
بگویید برای این رمزها از رمز عبور مهم خودشان استفاده نکنند.

`JWT_SECRET` و `ENCRYPTION_KEY` مقدار پیش‌فرض ندارند. اگر تنظیم نشده باشند،
عملیاتی که به آن‌ها نیاز دارد خطا می‌دهد. دلیلش این است که مقدار پیش‌فرضی که در یک
مخزن عمومی کامیت شده باشد، دیگر راز نیست.

## وضعیت پروژه

پروژه کار می‌کند و در حال استفاده است. چند بخش هم صادقانه ناتمام‌اند:

- فایل‌های آیکونی که `app/layout.tsx` و `public/manifest.json` به آن‌ها اشاره
  می‌کنند در مخزن نیستند. فهرستشان در [public/README.md](public/README.md) است.
- مسیرهای `/terms`، `/privacy` و `/about` در فرم ثبت‌نام لینک شده‌اند و در sitemap
  هم آمده‌اند، اما صفحه‌شان هنوز ساخته نشده است.
- مسیر `app/api/analytics/track/route.ts` فقط یک stub است که لاگ می‌گیرد و موفقیت
  برمی‌گرداند. مسیر `app/api/check-username/route.ts` هم کار می‌کند اما هیچ‌کس آن را
  صدا نمی‌زند؛ فرم ثبت‌نام آزاد بودن نام کاربری را مستقیم از Supabase می‌پرسد.
- جدول‌های `document_comments` و `user_follows` در ساختار دیتابیس هستند اما رابط
  کاربری ندارند.
- Supabase پکیج `@supabase/auth-helpers-nextjs` را که این پروژه از آن استفاده
  می‌کند کنار گذاشته و جایش `@supabase/ssr` را توصیه می‌کند. مهاجرت به آن
  مهم‌ترین کار باقی‌مانده در این پروژه است. توضیحش در
  [docs/architecture.md](docs/architecture.md) آمده است.
- تست خودکار وجود ندارد. CI فقط lint، typecheck و build را اجرا می‌کند.
